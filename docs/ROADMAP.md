## Interchange export and station panoramas (Oct 26, 2026)

**Large cloud panorama rendering.** Building a panorama for a large station is now available as a durable `panorama_render` worker task instead of blocking the Studio viewer's request. The API reuses an active request with the same cloud/station/render settings and returns valid cache hits immediately; the viewer displays task progress while the worker streams the station in blocks. The legacy image GET remains available, while the Studio viewer uses the queued path. Verification on synthetic stations: panorama API/renderer focused suite **38 passed**, including queue → headless worker → cache-hit and monotonic block progress. A live worker then streamed all **43,500,000 points** from the existing workshop PLY derivative, completed at 100%, and the matching PNG GET returned HTTP 200 (1,097,280 bytes). That render used 1024×512 output; the existing 2048×1024 cache was also served immediately. Frontend tests and `tsc -b` passed; production Vite build passed (1,983 modules). This does not close Stage 11: the native 297.9M-point FARO source was not rerendered, GPU kernels on CUDA hardware and multi-host workers with shared broker/Postgres/object storage remain unverified, as does host acceptance. Evidence: [`STAGE11_PANORAMA_WORKER_2026-10-26.json`](validation/STAGE11_PANORAMA_WORKER_2026-10-26.json).

**Cloud export.** `POST /clouds/{id}/export` writes E57, LAS, LAZ, PLY or XYZ as a durable worker task. Every export is read back with SCAN's own reader, the maximum coordinate deviation is measured and reported with the per-format tolerance, and an export that exceeds its tolerance fails instead of being delivered. The source `positions.npy` is opened read-only; a derived (cleaned) cloud can be exported instead of the original. The Studio export tab list the finished exports with their measured deviation and offers a download. `backend/tests/test_cloud_export.py` covers the measured round-trip, the source hash staying unchanged and the refusal of a non-finite cloud.

**Station panoramas.** Station entries come from the import metadata (`station_row_ranges`) or, when the cloud has no station split, from the whole cloud. The image is either an uploaded equirectangular photograph — validated for format, pixel size, 2:1 aspect and checksum — or a panorama rendered from the stored points, which reports its coverage, colour source, rendered/source point counts and stride. Measurement between two panorama pixels uses the depth map of that render; a direction without points returns HTTP 422 with the reason rather than a distance. The viewing point is the measured centroid of the station's points, and the API says so, because the format readers do not persist the scanner's optical centre. The Studio panel lists the stations, switches between the photograph and the cloud render, uploads a photograph with an azimuth offset, and shows the measured distance with its precision. `backend/tests/test_station_panorama.py` and `test_station_panorama_api.py` cover catalogue, render, pick, measurement, upload validation and the honest 422.

**Real-cloud acceptance of panoramas (297.9M points).** `backend/scripts/evaluate_station_panorama_real.py` runs the panorama chain over HTTP against the project database and the real `1.rcs` cloud. It found three things and each was fixed rather than explained away:

1. *Sparse sheet.* The renderer subsampled every station to 4M points, so a 297.9M-point station covered only **26.9 %** of a 2048 px sheet (**12.2 %** at 4096 px). `render_cloud_panorama_streaming` now reads the station in 8M-row blocks and keeps only the nearest depth and colour per pixel: **73.9 %** and **69.8 %** coverage, full resolution (no stride), ~50 s per sheet, 1.32 GB peak USS while RSS also holds the memory-mapped 4.5 GB cloud (reclaimable), 0.03 s from cache.
2. *Slow z-buffer.* Sorting every block far-to-near took 92 s; `np.minimum.at` plus an equality mask produces a bit-identical sheet in 53 s on the same data.
3. *Unstable measurements.* The same two pixels measured on 2048 and 4096 sheets disagreed by up to 11.4 m, because in this hall 43 % of filled pixels border a depth discontinuity (thin pipes and trusses in front of walls). `panorama_pick` now reports the largest gap between neighbouring depths and marks the pixel `stable: false`; `measure` returns `reliable: false` with a warning instead of a bare number, and Studio shows it in amber. On the 12 sampled pairs every flagged steep case was the one that moved (9 pairs), while the 3 continuous-surface pairs stayed within 131 mm (median 35 mm, ~1 pixel at their distances).

Fidelity is not assumed: the script recomputes the whole depth sheet from the cloud with independent code and compares pixel sets and values — 1,549,072 pixels, identical set, **0.0 m** maximum difference over 228.4M reprojected points. `measure` also returns `point_local` next to the world point, mirroring `pick`. Evidence: [`STATION_PANORAMA_REAL_*.json`](validation/STATION_PANORAMA_REAL_20261026T194138Z.json) with a downscaled sheet next to it. The cloud still has no station split — RCS imports as one piece, so the catalogue honestly reports a single `station_source="cloud"` station, and the report says so.

**AutoCAD acceptance.** `backend/scripts/validate_autocad_accoreconsole.py` builds a representative sheet, converts it through the production `convert_dxf_to_dwg_accore` path and then has AutoCAD itself open the produced DWG and report the marker text, its insertion point, its layer and the entity count. On this host the run passed: DWG header `AC1032`, 22,023 bytes, AutoCAD `ACADVER 25.1`, marker found once with 0.0 m coordinate deviation. The protocol is written to `docs/validation/AUTOCAD_ACCORECONSOLE_*.json`; when AutoCAD is absent the script reports `unavailable` instead of a pass.

Uninstall removed TEMP data/installation and the HKCU record. The existing release EXE remains unchanged. The new candidate is unsigned and only validated on Windows 10, so Stage 12 remains open. Evidence: [`current source install smoke`](validation/STAGE12_CURRENT_SOURCE_INSTALL_SMOKE_2026-10-26.json).

Замена выбирает по одному детерминированному случайному индексу из каждого равного интервала источника; временные массивы ограничены чанком 500 000 строк, результат отсортирован и уникален. Для миллиардных облаков поведение стратифицированного выбора тоже остаётся O(target), без Floyd hash table.
