## Как размечать

1. Открой облако пилота, выбери колонну в списке или 3D и работай в карточке «Эталонная разметка». Сначала просмотри исходные точки, сечения и грани. Интерфейс намеренно не копирует кандидатные размеры или каталожную марку.
2. Введи имя разметчика, уникальный `physical_instance_id` и независимый `type_label`; выбери форму и роль. Один физический ID нельзя назначить нескольким кандидатам без предварительного разбора дубликата.
3. Заполни видимые и закрытые грани, длинную/короткую стороны в мм и при необходимости измерения на нескольких отметках Z. Для размеров укажи источник `manual_cloud` или `field_measurement`; допустимо оставить размеры пустыми, если они не видны.
4. Если тип нельзя определить, выбери `unknown` и укажи причину. Для ложного/нецелевого кандидата выбери `excluded` и объясни решение. Сохраняй только после проверки; каждое сохранение создаёт новую ревизию.
5. Сохранение не меняет распознанную геометрию и привязывает аннотацию к хешу источника, облачного манифеста и списка кандидатов. При изменении хеша API отклонит устаревшую запись; прошлые ревизии доступны из истории старых снимков.
6. Скачай «Эталон JSON» и оцени его только с BIM JSON того же облака и снимка. CLI проверяет cloud manifest и SHA снимка, а также сохраняет SHA точного JSON-файла. `mixed` означает, что в одной разметке есть обмеры и по облаку, и полевые.
7. Оценка по ручной разметке облака проверяет сопоставление типов среди существующих кандидатов. Для точности сканирования в натуре нужны отдельные полевые контрольные размеры; инженерный допуск пока не задан.

## Воспроизводимые команды

Запускать из корня репозитория; каждый --out должен быть новым JSON-файлом.

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_column_types.py template --source data/validation/pilot-A/revit/scan2bim-pilot-A.json --out data/validation/pilot-A/column-type-evaluation/annotations.new.json
.\.venv\Scripts\python.exe scripts/evaluate_column_types.py evaluate --source data/validation/pilot-A/revit/scan2bim-pilot-A.json --annotations data/validation/pilot-A/column-type-evaluation/annotations.reviewed.json --linear-mm 2 5 10 --relative 0.005 0.01 --out data/validation/pilot-A/column-type-evaluation/report.reviewed.json
```

Инструмент не изменяет снимок, исходные точки, рабочую БД, назначения типов или каталог. Существующий выходной файл не перезаписывается. После смены версии снимка прежний эталон не принимается автоматически. Отчёт хранит контрольные суммы снимка и разметки.

## Определение метрик

Метрики рассматривают пары колонн с независимым известным типом, без требования совпадения имён меток алгоритма и инженера. TP — пара одного эталонного типа, объединённая алгоритмом. Ложное объединение — пара разных эталонных типов в одной группе. Ложное разделение — пара одного эталонного типа в разных группах либо с отсутствующим назначением. precision = TP / (TP + ложные объединения), recall = TP / (TP + ложные разделения). Неопределённый знаменатель даёт null, а не 100%.

Неизвестные/ожидающие разметки эталоны не становятся правильными автоматически: отдельно показаны labeled/unknown/pending/excluded/unannotated, охват эталона и охват предсказаний на известных эталонах. При наличии независимых размеров выводятся остатки long/short в мм, MAE, смещение, RMSE и максимальная абсолютная ошибка. Пары считаются через таблицы сопряжённости без перебора всех O(n²) пар.

Это метрики группировки уже имеющихся кандидатов. Они не измеряют пропущенные физические колонны, точность детекции или геодезическую точность облака. Для этого нужны отдельная полная инвентаризация и полевые контрольные размеры.

## Текущий результат

`pending-reference-report.v2.json`: 2/5/10 мм × 0,5/1% = 6 сочетаний. В каждом 16 предложений, все одиночные. Независимых меток 0, pending 16; precision/recall=null, engineering_accuracy_status=not_assessed. Это запуск инфраструктуры, не оценка качества. Производственные пороги не выбраны.

Перепроверка 24 октября 2026: `pending-reference-report-20261024.json` заново построил шесть сочетаний на том же зафиксированном снимке. Все 16 эталонов по-прежнему pending, метрики остаются null/not_assessed; это подтверждает состояние шаблона, а не точность классификации.

Из этого следует проверить, соответствуют ли текущие коробки действительным сечениям и отдельным физическим колоннам. Увеличивать порог только ради 3–4 типов нельзя; число типов должно следовать из наблюдений. Следующий блок — независимые поперечные сечения и разбор слишком широких/ступенчатых/перекрывающихся кандидатов.

## Срез зарегистрированного облака 1.rcs — 23 октября 2026

- Выполнен read-only sweep по уже сохранённой производной выборке: 40 млн строк из примерно 297,873,927 исходных точек. В базе нет SHA-256 исходного RCS; исходник в этом анализе не открывался.
- После исключения одного отклонённого элемента осталось 266 кандидатов колонн: 264 геометрических (`unreviewed`) и 2 вручную скорректированных (`manual`, `corrected`). У двух ручных строк сечение inferred без `section_status`; sweep использует только 33 point-measured геометрических наблюдения минимум по двум осям. Среди 266 кандидатов у 33 есть сечения с point-derived измерениями двух осей или больше; 34 имеют частичное измерение одной оси, 34 — только грубую сетку, 163 — неизвестное/неподтверждённое сечение, у 2 сечение отсутствует.
- При относительном пороге 1% число повторяющихся предложений менялось так: линейные 2 и 5 мм — 0 групп; 10 мм — одна пара; 25 мм — две пары; 50 мм — 6 групп (размеры 4, 3, 3, 2, 2, 2); 75 и 100 мм — по 8 групп. Полные IDs, остатки и параметры сохранены в `data/validation/pilot-A/column-type-evaluation/real-1rcs-tolerance-sweep-20261023.json`.
- Это анализ чувствительности кластеризации, не точность и не подтверждение типов. Независимых физических ID, инженерных меток и полевых размеров нет; облако децимировано. Production-порог не выбирался. Полный 1.rcs остаётся примерно 297,9 млн точек.
- Изолированный вызов `GET /api/v1/clouds/{cloud_id}/column-types` на копии текущей БД вернул HTTP 200: при API default 5 мм — 33 singleton-предложения и 0 повторяющихся групп; подтверждённых типов нет. Рабочая БД для этого smoke-check не использовалась.
- Утилита типизации дополнительно исключает отклонённые и инвалидированные элементы даже при прямом вызове вне API; регрессионный тест проверяет, что такие записи не образуют proposal.
- Независимые annotation GET/save/export/history endpoints также исключают `invalidated_synthetic_ground_truth`; API-тест проверяет, что такие строки не выдаются, не принимаются для записи, скрываются из архивной истории и не входят в reference export.
